# ko-pii-public-v1 실측 — span localizer 후보 평가

- 실험일: 2026-08-31 (KST)
- 대상: [`ehd0309/ko-pii-public-v1`](https://huggingface.co/ehd0309/ko-pii-public-v1)
  (revision `2b975fbafafc3d6936a5ac62f6ae57137681e4c8`)
- 하드웨어: GB10 (통합 메모리 121.7 GiB, 20 코어, driver 580.142)
- 스택: `torch 2.13.0+cu130` (aarch64), `transformers 5.16.1`, Python 3.12.13
- 범위: 자원·지연 실측, 한국어 의료/보험심사 도메인의 탐지·오탐 측정, 후처리 설계 검증
- 수행하지 않은 것: 코드 변경, 서빙 구성, 파인튜닝, 실제 corpus 평가

## 왜 봤는가

gardevoir의 마스킹은 span이 있어야 성립한다. 모델 티어의 Shieldstral은 `yes`/`no`만
생성하므로 위치를 주지 못하고, 그래서 `GUARDRAIL-018`이 `model → verdict(mask)` 를
저작 시점에 거부한다(`2026-08-27-masking-localizer-survey.md`). 현재 마스킹은 전적으로
RE2 regex가 담당하며, 남은 한계는 **라벨 없는 사람 이름과 축약 주소**다. 이 모델은
23종 PII를 token classification으로 판정하므로 정확히 그 빈칸의 후보다.

## 결론

1. **자원은 논점이 아니다.** BF16 가중치 2.80 GB, 총 ~3.3 GB. 이 호스트 가용량의 6%.
2. **GPU가 필수다.** CPU는 15토큰에 300 ms, 384토큰에 2.2초로 요청 경로에 못 쓴다.
   따라서 CUDA torch가 필요하고, 이는 게이트웨이 in-process 적재를 배제한다(§아래 D).
3. **정형 PII를 이 모델에 맡기면 안 된다.** 라벨이 없는 문맥에서 주민등록번호를 놓쳤다.
   regex는 문맥과 무관하게 잡는다. 정형은 규칙 티어가 계속 소유해야 한다.
4. **비정형(이름·주소)은 잘 한다.** 표기 변형(`김 씨`, `~님`, `~환자`)까지 잡는다.
   이것이 이 모델을 들일 유일한 이유다.
5. **의료 도메인 오탐이 광범위하다 — 전 범주 37%.** 약제뿐 아니라 검사명·치료재료·
   장비·질환명까지 사람 이름으로 읽는다. 사전을 범주마다 붙이는 방식은 닫히지 않는다.
6. **오탐은 닫힌 긍정 게이트로 96% 제거된다.** 성씨(닫힌 집합) + 2~4음절 조건이
   오탐 23건 중 22건을 걸러낸다. 사전은 주 기제가 아니라 잔여 패치로 내려간다.
7. **원 span은 그대로 마스킹에 쓸 수 없다.** 서브워드 경계가 어긋나 부분 누출이 생긴다.
8. **채택 판단은 아직 못 한다.** 아래 §H의 두 숫자가 실제 corpus에서 측정되어야 한다.

`max_tokens` 개념이 없는 분류 모델이라 전방 통과 1회를 잰다. warm-up 3회 후 측정.

| --- | ---: | ---: | ---: | ---: |
| 짧은 문장 | 15 | 456.6 ms | 299.7 ms | **42.9 ms** |
| 의료 문장 | 36 | 701.8 ms | 543.6 ms | **52.6 ms** |
| 중간 | 72 | 1137.3 ms | 790.3 ms | **74.6 ms** |

| 최대 | 384 | 2198.1 ms | 1605.8 ms | **82.1 ms** |

실사용 PII 문장(61토큰) 반복 측정 n=30: **p50 53.1 ms, p95 55.1 ms** (min 51.0, max 56.5).

고정 오버헤드가 ~40 ms이고 토큰당 비용은 작다(72→384 토큰이 74.6→82.1 ms). 8층 ×
128 expert 라우팅의 커널 실행 비용으로 보인다.

**비교 기준**: 규칙 티어 p50 0.26 ms, Shieldstral 판정 p50 42.5 ms(짧은 문장) /
53.4 ms(약 1,400자). 이 모델은 Shieldstral과 같은 자리수다.

**CPU가 7~20배 느린 이유는 MoE 라우팅으로 추정한다** — 128 expert에 대한 gather가
CPU에서 효율적인 경로를 타지 못하는 것으로 보인다. 프로파일링으로 확인하지 않았다.

## D. 배치 결론 — in-process 배제

CPU 탈락 → CUDA torch 필수 → 다음 세 가지가 따라온다.

1. **이미지**: 게이트웨이 현재 321 MB. CUDA torch 환경이 4.6 GB이므로 ~5 GB가 된다.
2. **기동**: 모델 로드 18.7 s가 `/healthz` 준비를 늦춘다. compose `depends_on` 사슬과
   콘솔 기동이 전부 그만큼 밀린다.
3. **실패 도메인**: gardevoir는 요청 경로 위의 프록시다. 현재는 모델 실패가
   `violated=None` → fail-mode로 **그 체크만** 무력화한다. in-process면 torch OOM이
   게이트웨이 전체를 내려 모든 요청이 죽는다.

따라서 **gardevoir 자기 compose 스택의 별도 컨테이너**가 맞다. 참고로 이 모델에는
vLLM이 도움이 되지 않는다 — 384 토큰 token classification이라 배칭·paged attention이
벌어주는 것이 없다. 서버는 어느 쪽이든 직접 쓰게 된다.

## E. 탐지 실측

임계값은 모델 카드 권고인 0.93을 썼다. `date_of_birth`는 이 도메인에서 마스킹 대상이
아니므로 껐다.

### E.1 라벨이 붙은 단순 템플릿 — 미탐 0/12

`주민등록번호`, `외국인등록번호`, 휴대폰, 유선전화, 이메일, 계좌번호, 카드번호,
도로명 주소, `환자명:` 이름, **라벨 없는 이름**, 건강보험증번호, 환자 ID 전부 탐지.
신뢰도 0.994~1.000.

### E.2 의료 음성 — 오탐 4/12

가려지면 안 되는 출력에 대한 결과다.

| 케이스 | 결과 |
| --- | --- |
| 약제 코드 `5-FU` · EDI 수가코드 `Q1234` `KK020` · 상병코드 `C16.9` | allow |
| 고시번호 `제2024-123호` · 용량 `100-200mg` · 병원명 · 기관명 | allow |
| `2026-08-28 에 투여를 시작했다` | **`date_of_birth` @1.000** |
| `이리노테칸 180mg/m2` | **`person_name` = `이리` @0.967** |
| `키트루다는 위암 2차...` | **`person_name` = `키` @0.950** |
| `서울시 강남구 소재 요양기관` | **`address` 부분 매치 @0.955** |

날짜는 신뢰도 1.000이라 임계값으로 막을 수 없다. 라벨을 끄는 것이 유일한 해법이다.

### E.3 섞인 문장 — 여기서 깨진다

E.1의 "미탐 0"은 **라벨 붙은 단순 템플릿**에서 나온 값이다. 실제 심사 답변처럼
이름·식별번호·약제가 한 문장에 섞이면 결과가 달라진다.

```
김철수(900101-1234567) 환자에게 허셉틴을 투여하고 심평원에 청구했다.
→ ▮(900101-1234567) 환자에게▮셉틴을 투여하고 심평원에 청구했다.
     ↑ 주민등록번호 누출              ↑ 약제명 파괴
```

**주민등록번호 미탐이 이 실험에서 가장 중요한 결과다.** 같은 값을
`주민등록번호 900101-1234567 입니다` 로 주면 1.000으로 잡는다. 라벨이 없고 괄호 안에
있으면 놓친다. regex `\b\d{6}-[1-4]\d{6}\b` 는 문맥과 무관하게 잡는다.

7개 혼합 케이스 중 4건은 정상 처리됐다. 이름 표기 변형이 특히 좋았다 —
`김 씨`(1음절), `박민수님`, `최지훈 환자` 전부 탐지. 의사명(`이영희 주치의`)도
함께 가리는데 이는 결함이 아니다.

## F. 오탐의 범위 — 약제에 국한되지 않는다

"약제 사전으로 억제하면 된다"가 성립하는지 확인하기 위해 의료 용어 전 범주를 쟀다.
템플릿은 `{용어} 를 적용하여 산정한다.` 로 통일했다.

| 범주 | person_name 오탐 | 예 |
| --- | ---: | --- |
| 약제(음역) | **5/6 (83%)** | 이리노테칸, 허셉틴, 젬시타빈, 니볼루맙, 엘로티닙 |
| 검사명 | **6/11 (55%)** | 크레아티닌, 빌리루빈, 알부민, 페리틴, 프로칼시토닌 |
| 장비·기법 | 3/7 (43%) | 감마나이프, 사이버나이프, 피이티씨티 |
| 치료재료 | 5/12 (42%) | 스텐트, 콜라겐매트릭스, 폴리프로필렌메쉬 |
| 질환·소견 | 3/8 (38%) | 아데노카시노마, 멜라노마, 글리오블라스토마 |
| 치료재료(상품명) | 1/9 (11%) | 바이오패치 |
| **수술·행위** | **0/10 (0%)** | 복강경담낭절제술, 관상동맥우회로조성술 … |
| **합계** | **23/63 (37%)** | |

**수술·행위가 0%인 것이 결정적 단서다.** 순한자어 복합어는 사람 이름으로 읽히지 않는다.
오탐이 나는 것은 전부 **한글 음역어(외래어)** 다.

즉 오탐 대상은 "약제"가 아니라 **의료 외래어 전체**이며, 신약·신재료·신검사·신장비가
계속 생기므로 **닫히지 않는 집합**이다. 범주별 부정 사전을 쌓는 방식은 끝나지 않는다.

## G. 후처리 설계 — 닫힌 긍정 게이트

부정 목록(무엇이 이름이 **아닌가**)은 열려 있지만, 긍정 조건(무엇이 이름일 **수
있는가**)은 닫혀 있다. 한국 인명은 형태가 제약되고 의료 용어는 아니다.

```
person_name 스팬은 (첫 음절 ∈ 성씨 목록) AND (2~4음절) 이어야 한다
```

**측정: 오탐 23건 중 22건 제거 (37% → 1.6%).** 통과한 것은 `허셉틴` 하나뿐이다
(허=성씨, 3음절). 성씨는 약 300개의 닫힌 집합이며 의료 용어가 늘어도 변하지 않는다.

잔여는 사전으로 처리한다. 규칙은 겹침 판정이다 — 오탐 스팬이 `허`, `이리노` 처럼
부분이기 때문이다.

```python
def suppress(text, spans):
    ranges = drug_ranges(text)              # 사전 항목이 본문에 나타난 구간
    return [(a, b, k, s) for a, b, k, s in spans
            if not (k == "person_name"
                    and any(a < rb and b > ra for ra, rb in ranges))]
```

32항목 시연 사전으로 측정: 약제명 오탐 **12/31 → 0/31**, 실제 이름 미탐 **0/7**(부작용
없음), 비용 **0.0052 ms**(추론 53 ms의 0.01%). 운영에서는 공개 약제 목록을 적재하고
조회를 RE2 alternation 한 번으로 대체한다(이 저장소는 `import re2` 가 규칙이다).

### G.1 게이트가 무는 대가

**외국인 환자 이름을 놓친다.** 한국 성씨로 시작하지 않는 표기는 게이트에서 탈락한다.
이 모델에 `foreigner_id` 라벨이 따로 있다는 것 자체가 외국인 환자를 전제하는 도메인임을
말한다. 같은 문장에 확정 PII가 있으면 게이트를 우회시키는 식의 조건부 완화가 필요하며,
아직 설계·측정하지 않았다.

### G.2 문맥 앵커를 필수 조건으로 쓰면 안 된다

`환자명:`, `환자 X`, `X 님`, `수급자 X`, `보호자 X` 6종 앵커는 전부 탐지됐다. 그러나
앵커 없는 `김철수는 2주기 투여했다`, `담당은 이영희다`, `김철수와 상담했다` 도 전부
탐지됐고, **그것이 regex가 못 하던 부분**이다. 앵커는 필수 조건이 아니라 게이트를
완화하는 추가 증거로 써야 한다.

## H. 스팬 경계 — 원 출력은 마스킹에 쓸 수 없다

서브워드 offset이 어절 경계와 어긋나 부분 누출이 생긴다.

```
원문: 주소 서울특별시 송파구 올림픽로 43길 88 입니다.
적용: 주소[개인정보 삭제됨] 송[개인정보 삭제됨] 올[개인정보 삭제됨] 입니다.
                          ↑ 누출        ↑ 누출

원문: 환자ID P-2026-00123 로 조회했다.
스팬: ' P-2026-'   →  00123 이 그대로 남는다
```

**가린 것처럼 보이면서 실제로 새는** 형태이므로 안 가리는 것보다 나쁘다. 인접 동일
라벨 병합과 어절 경계 확장이 필수다.

## I. 업계 관행 — 후처리는 예외가 아니라 아키텍처다

이 문서가 도출한 층들은 전부 기존 프레임워크에 이름이 있다. Presidio Analyzer는
정규식·deny-list·checksum·context·custom logic·NER를 **조합하는 것으로 정의**되며
(`2026-08-28-guardrail-landscape-survey.md` §6), 공식 문서는 여러 NER와 규칙 recognizer를
함께 쓰라고 권고한다.

| 이 문서의 층 | Presidio의 이름 |
| --- | --- |
| 성씨+길이 게이트 | `PatternRecognizer` 의 validation / invalidation logic |
| 약제·재료 사전 억제 | allow-list |
| 문맥 앵커를 추가 증거로 | `LemmaContextAwareEnhancer` (`ContextAwareEnhancer`) |
| 정형은 regex, 비정형은 모델 | `PatternRecognizer` + `EntityRecognizer` 조합 |
| 임계값 0.93 | score threshold |
| 스팬 경계 복구 | Anonymizer는 span 목록을 입력으로 받는다 — 품질은 호출자 책임 |

**따라서 후처리량 자체는 이 모델의 결함이 아니다.** 실제 비용은 다른 데 있다 —
Presidio의 context word·validation 자산은 영어 기준으로 축적된 것이고
([공식 Analyzer 문서](https://presidio.dataprivacystack.org/analyzer/)),
한국 성씨 목록·행정구역·약제 목록·조사 앵커는 우리가 채워야 한다.

**대안**: Presidio를 프레임으로 채택하고 이 모델을 `TransformersRecognizer` 로 꽂으면
deny/allow-list·context enhancer·threshold를 얻고 우리는 한국어 validator만 쓰면 된다.
대가는 의존성과 spaCy 영어 엔진이며 한국어 경로는 미검증이다. 측정하지 않았다.

## J. 권고

채택 여부를 지금 결정하지 않는다. **실제 심사 답변 corpus(수백 건)로 두 숫자를 재면
결정이 떨어진다.**

1. **regex가 놓치는 이름·주소가 실제로 몇 %인가.** 0에 가까우면 3.3 GB와 53 ms를
   들일 이유가 없다. 이 숫자는 이 논의의 전제였으나 한 번도 측정된 적이 없다.
2. **후처리 3층을 붙인 뒤 의료 용어 오탐이 0인가.** 답변 훼손은 배포 실패 조건이다.

채택한다면 역할 분담은 다음과 같다.

| | 담당 | 근거 |
| --- | --- | --- |
| 정형 (주민번호·외국인등록번호·카드·계좌·전화·이메일) | **regex 단독** | 모델은 문맥이 없으면 미탐(§E.3) |
| 비정형 (이름·주소) | **모델 + 후처리 3층** | regex가 구조적으로 못 하는 부분 |
| `date_of_birth` | **끔** | 이 도메인에서 마스킹 대상이 아니며 오탐 1.000 |
| 약제·수가·상병·행위 코드 | **건드리지 않음** | 게이트 + 잔여 사전으로 억제 |

## L. 이 실측의 한계 — 반드시 감안할 것

**여기 나온 모든 탐지·오탐 수치는 저자(작성 에이전트)가 직접 작성한 약 130개 문장에
대한 값이다.** 실제 corpus가 아니며 용도에 맞게 구성된 표본이므로 유리하게 나온다.

실제로 한 번 깨졌다: §E.1에서 "미탐 0/12"였던 것이 §E.3의 섞인 문장에서 주민등록번호
미탐으로 무너졌다. 모델 저자가 외부 데이터(KDPII 대화체 홀드아웃)로 공개한 값은
**F1 0.858**(precision 0.859, recall 0.857)이고, 모델 카드도 짧은 대화체가 v2보다
약하다고 적는다. 길이별 합성 평가의 0.99+는 **모델 저자 본인의 합성 데이터**에 대한
값이다.

실제 성능은 저자의 0.858과 이 문서의 값 사이 어딘가로 보아야 한다.
